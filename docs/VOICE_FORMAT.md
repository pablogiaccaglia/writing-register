# The voice format

A voice tells a model how one person wants to read the text written for them. writing-register reads a voice in one of two shapes: a single markdown file, which is the easiest way to start, and a directory of rule files, evidence and decisions, which is easier to maintain once the voice has grown. Both shapes give the model the same thing, one block of text called the core. This page describes both shapes, the checks `wr voice check` runs on a directory, and the commands that work on a voice. [BUILDING_A_VOICE.md](BUILDING_A_VOICE.md) explains how to decide what goes into one.

## A single-file voice

A single-file voice is a markdown file with a line `<!-- wr:end-of-core -->` in it. Everything above that line is the core, which the model receives in every session, every subagent and every rewrite. Everything below it is for the people who maintain the voice: where each rule came from, examples, decisions. The model never receives it. A file without the marker is all core.

```markdown
# Voice: Station team

## Register

- No em dashes. Use a comma, a colon or a new sentence.
- Say what a reading measures before giving its value.

<!-- wr:end-of-core -->

## Where these rules came from

"what is this 4.2??? 4.2 of what" (2026-08-03, on the weekly report)
```

## A voice directory

A directory holds the same voice split by subject, so that a change touches only the file it concerns and every rule keeps its evidence beside it.

```
voice/station-team/
  voice.toml        format, name, budget, whether evidence is required, the order of rule files
  rules/            what the model receives, in the manifest's order; nothing else reaches it
    reader.md
    register.md
    kinds.md
    kinds/reports.md
  evidence/         for people: dated quotes, before-and-after examples, measurements
  decisions.md      for people: where requests pulled in different directions
  about.md          for people: how the voice was built
  maintaining.md    for people: how to change it
voice/station-team.md   generated by `wr voice build`, read-only
```

The manifest, `voice.toml`, has five settings and refuses any other, so a typo cannot quietly empty the voice:

```toml
format = 1
name = "Station team"
budget = 12000          # optional: the most characters the core may have
evidence = "required"   # or "optional", the default
order = ["reader.md", "register.md", "kinds.md", "kinds/reports.md"]
```

The core is built from the rule files in the order the manifest lists them. It opens with `# Voice: <name>`, and each rule file's first line, `# Title`, becomes a `##` heading. A file inside a folder, such as `kinds/reports.md`, belongs to the rule file of the same name (`kinds.md`) and renders as a paragraph under that file's heading, opened by its title in bold. So a directory produces exactly the kind of text a single file holds, and the runtime reads only the manifest and `rules/`, never the evidence.

`wr voice build` writes the whole voice to one file beside the directory: the core, the end-of-core marker, then the about, evidence, decisions and maintenance files. That file is marked as generated and is itself a valid single-file voice with the same core, so a configuration that points at it gets the same voice. Edit the directory, never the generated file; `wr voice check` reports a generated file that is out of date.

## Rule lines

Every line of a rule file, after the title, is a rule, and every rule starts with a marker that names it:

```markdown
# Register

- {#register.no-dashes} No em dashes. Use a comma, a colon or a new sentence.
- {#register.units refines=register.no-dashes} A range of readings keeps its hyphen, as in 10-20 hPa.
```

- **The identifier** is `stem.slug`, where the stem is the rule file's name (`register` for `register.md`, `reports` for `kinds/reports.md`). Evidence and decisions point at rules by these identifiers.
- **`refines=`** marks a rule as a more specific case of another. Where both apply, the specific rule wins, so the rule it refines must come earlier in the core.
- **Markers never reach the model.** They are removed when the core is built, where they would only cost characters and read as a database.
- **Layout.** A rule can be a list item or part of a paragraph, and one line may hold several markers. Consecutive lines without a blank line between them are joined into one paragraph.

## Evidence entries

Evidence files live under `evidence/`, usually one per rule file. Each entry is a second-level heading, a `Rules:` line naming the rules it supports, a blank line, and a body that carries at least one date:

```markdown
## Numbers with no unit
Rules: register.units, reports.what-it-measures

> "what is this 4.2??? 4.2 of what" (2026-08-03, on the weekly report)

| Before | After |
|---|---|
| "Pressure rose 4.2." | "Pressure at the ridge station rose 4.2 hPa in an hour." |
```

A dated entry lets a later reader tell a correction made last week from one made a year ago, and it lets the checker notice when a decision is older than the evidence behind it.

## Decisions

`decisions.md` records where the owner's requests pulled in different directions and what was chosen, so nobody reopens the question by accident. Each entry is a heading, a header block and a body:

```markdown
## Results or method first?
Rules: reports.results-first, reports.method
Decided: 2026-09-10
Confirmed: 2026-11-02
Status: default, open to change

A short version of the results first, then the method, then the detailed results.
```

`Rules:` and `Decided:` are required. `Confirmed:` records a later date on which the decision still held. `Status:` is free text. `Retires:` names rules the decision removed, so an old reference to them is not an error.

## What `wr voice check` enforces

Each check exists because the failure it catches happened or would be silent.

| Level | Check | The failure it prevents |
|---|---|---|
| error | The manifest parses, has only the five settings, `format = 1`, a name, a list for `order`, a positive budget | A typo that empties the voice |
| error | Every file in `order` exists, and every file under `rules/` is in `order` | A rule file the model never receives |
| error | Only `about.md`, `decisions.md` and `maintaining.md` sit at the root | Rules written where nothing reads them |
| error | A file in a folder comes after its parent in `order` | A paragraph rendered under the wrong heading |
| error | Every rule line starts with a marker, and holds no HTML comment and no relative link | A comment reaching the model or cutting the view short; a link that breaks in the generated file |
| error | Identifiers are `stem.slug`, match their file, are unique, and two files do not share a stem | Evidence pointing at the wrong rule |
| error | A `refines=` target exists, is not the rule itself, and comes earlier | A specific rule the model reads before the general one |
| error | No sentence of three words or more appears in two rules | The same rule stated twice and edited once |
| error | The core fits the budget; the message lists every rule file's size | A voice that grows without anyone deciding it should |
| error | Every evidence entry and decision has a `Rules:` line naming real rules, or rules a decision retired | Evidence for a rule that no longer exists |
| error | Every evidence entry carries a date, and every decision a `Decided:` date | Provenance nobody can place in time |
| error | With `evidence = "required"`, every rule is named by an evidence entry or a decision | A rule added with nothing behind it |
| error | No decision retires a rule that still exists | A rule both kept and removed |
| error | The generated view is current | Someone editing the wrong copy |
| warning | A rule contains a date or "measured on" | A measurement travelling in every session instead of sitting in the evidence |
| warning | A decision is older than the newest evidence for its rules | A decision nobody revisited after new evidence arrived |
| advisory | Two rules share a phrase of three content words (`--overlaps` only) | Two rules that may say the same thing |

## Commands

| Command | What it does |
|---|---|
| `wr voice` | Shows the active voice and where that choice came from |
| `wr voice --core` | Prints the core the model receives |
| `wr voice check [target] [--overlaps]` | Runs the checks above; exits 1 on an error |
| `wr voice build [target] [--check]` | Writes the generated view; with `--check`, exits 1 when it is stale instead of writing |
| `wr voice show ID\|FILE [--voice-dir DIR]` | Prints a rule, or a rule file, with every evidence entry, decision and rule that points at it: what to read before changing it |
| `wr voice split FILE --into DIR` | Turns a single-file voice into a directory, keeping its core byte for byte |

A target is a voice directory, a voice name, or nothing for the active voice.

## Choosing a voice

The `voice` setting in `~/.config/writing-register/config.toml` names the voice:

```toml
voice = "technical-colleague"          # a voice in this clone's voice/ folder
# voice = "~/voices/station-team"      # a directory anywhere, by path
# voice = "~/voices/station-team.md"   # a single file, by path
```

A value holding a slash or ending in `.md` is a path, and a relative path is read from the folder that holds the configuration file. Any other value is a name looked up in the clone's `voice/` folder, where a directory wins over a file of the same name, because that file is the directory's generated view. Without the setting, or with `voice = "none"`, only the humanizer skill applies.
